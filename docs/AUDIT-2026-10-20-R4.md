## 一、#10：字幕从页面里读出来，Supadata 降级为备选

### 事实

改造之前，**每一个视频都要花一个 Supadata credit**。字幕只有一条获取路径：
Supadata 的付费接口。

Supadata 的免费额度是每月 100 条。这是用户自己的钱，而且字幕本来就在
**他正在看的那个 YouTube 标签页里**。

### 已修（`aac1550`）

播放器的 player state 里带着这个视频自己的字幕轨道地址（YouTube 已经签过名）。
worker 现在用 `chrome.scripting` 的 MAIN world 把这个地址读出来，直接从 YouTube
取字幕。

- **不用 Key**、**不消耗额度**、**字幕文字不出浏览器**。
- Supadata 保留为兜底：页面读不到、标签页关了、或者视频压根没有字幕轨道时。
- 所以 **Supadata Key 变成可选**：面板和设置页现在只要求 AI Key（摘要和翻译真的需要它）。

**产品上的后果**：免费额度用完时，产品不是「报错让你去充值」，而是**照常用**。

### 但这条路径其实一次都没有成功过（`aac1550` 写错了）

上面这一段是**合进来之后的样子**，不是**跑起来的样子**。2026-10-20 在真浏览器里
试的时候才发现：**这条路径从来没有取到过字幕，一次都没有。**

测试是绿的（23 个测试全过），因为测试用的假页面会回答任何一条 `/api/timedtext`
请求。真的 YouTube 不会。

**根因**：player state 里那条 `baseUrl` 是一份**模板**，不是播放器真正用的地址。
播放器请求字幕时会加上签名（PO token）和客户端身份参数，YouTube 对一份模板请求
返回的是**空 body**。实测 5 个视频、每一条字幕轨道，模板地址全部 0 字节。

**怎么定位的**：把浏览器里真正发出的那条 `/api/timedtext` 请求抓下来，
和模板地址逐个参数对比，再把参数一个个去掉试，找出到底哪几个是必需的：

| 参数 | 必需吗 |
| --- | --- |
| `pot` / `potc`（签名） | **必需**，没有就返回空 |
| `c` `cver` `cplayer` `cos` `cosver` `cplatform`（客户端身份） | **必需** |
| `lang` `kind` | 不在签名里，**可以改** |
| `variant` | **必须删掉**，指名要变体会返回空 |
| `xorb` `xobt` `xovt` `cbrand` `cbr` `cbrver` | 不需要 |

**修法**（`background.js`）：

1. 用 `performance.getEntriesByType("resource")` 找出**页面自己发过的那条**字幕请求，
   也就是带签名的那条。这是唯一能拿到字幕的地址。
2. `lang` 和 `kind` 不在签名里，所以把这条地址**指向产品要读的那条轨道**
   （英文优先），签名仍然有效。`variant` 删掉。
3. 页面还没发过字幕请求时（用户从没打开过字幕），让播放器去加载一条，
   然后等它发出来，最多等 4 秒。
4. 模板地址仍然作为最后的候选试一次。

**这一段是整轮里最重要的一次修复**，因为它把「多数视频不花钱」从一句宣传
变成了事实。之前那 23 个测试证明不了这件事——**假页面太配合了**。

**验收**：真浏览器里只配 AI Key、不配 Supadata Key，面板显示出真实字幕
（`0:02 I just b…`）。

### 变异验收（16 个，全部被抓住）

`tests/mutation-local-caption.py`（写这一节的时候是 16 个，后来又长到 23 个，
多出来的 7 个在第六节）

| 变异 | 结果 |
| --- | --- |
| 页面发过的字幕请求找不到 | 抓住 |
| 地址没有指向产品要读的那条轨道 | 抓住 |
| 指名去要一个翻译变体 | 抓住 |
| 不让页面去加载字幕轨道 | 抓住 |
| 用了别的视频的字幕请求 | 抓住 |
| 用了没有签名的字幕请求 | 抓住 |
| 从不试模板地址 | 抓住 |
| 跳过本地路径 | 抓住 |
| 去掉「标签页是不是这个视频」的检查 | 抓住 |
| 取第一条字幕轨道而不是英文那条 | 抓住 |
| 把兜底的结果扔掉 | 抓住 |
| 去掉「页面说不清就不信」的检查 | 抓住 |
| 面板又被缺失的 Supadata Key 卡住 | 抓住 |

| 那句话退回旧版本 | 抓住 |
| 丢掉「两件事都说」那句话 | 抓住 |

### 面板说的话也跟着变了

旧的产品在两条路都失败时说的是「请配置 Supadata Key」——它只说了**能修的那一半**，
把「这个视频本来就没有字幕」这一半藏起来了。用户去改设置、改完还是不行。

现在说的是两件事：这个视频没有能读到的字幕，而且没有设置兜底的 Key。

面板还多了一条信息：**只缺兜底 Key 时，面板照常工作**。开机时提示一次，
说完就走——一个一直挂在屏幕上的提示会被读成「出事了」。

这条提示**原来写错了**。它写的是「这个视频没有能读到的字幕」，
可它在**读到第一条字幕之前**就弹出来了：只要没配兜底 Key 就弹。
字幕其实读到了，屏幕上却写着「没有字幕」。真浏览器里验证的时候一眼就看出来了。

现在分成两句，各说各的：

- **开机提示**（还没读字幕）：「没有设置 Supadata 密钥。字幕直接从页面里读，不花钱；
  只有页面读不到字幕的视频，才需要补一个密钥兜底。」——这句话不管字幕读没读到都成立。
- **死胡同**（两条路都失败）：「这个视频没有能读到的字幕，也没有设置 Supadata 密钥作为兜底。」

开机提示也不再是**红色的错误条**：它是一条说明，4 秒后自己消失。
红条要用户点掉才走，而用户什么都没做错。

### 一条我自己写出来的缺陷（`d05b63d`）

本地路径信任「标签页现在在放什么」。但面板问的视频和标签页的视频可能不是同一个：
用户 navigates 的瞬间，请求已经在路上了。

结果是**最坏的一种错**：标题对、时间戳对，字幕属于另一个视频。没有人会发现——
文字读起来完全通顺，只是和这个视频无关。

修法：player response 会说它正在放哪个视频，worker 拿它和被问的视频对。
对不上、或者页面说不清，就退回 Supadata——那条路是**按视频 id 问的**，所以不会答错。

### 变异验收

第一个版本的检查有一个洞：页面不说自己是谁时，测试也因为 id 对不上而通过，
等于没测到「页面说不清」这一条。第一版的测试因此改成了**只传空 id**，
把两条检查分开测。两条都变红才算数。

## 二、#12：超过一小时的视频，时间戳是错的

### 事实

`formatTimestamp` 只算到分钟：

```js
const minutes = Math.floor(total / 60);
return `${minutes}:${String(total % 60).padStart(2, "0")}`;
```

一个 90 分钟的视频，第 90 分钟和第 150 分钟**都显示成 `90:00`**。
用户点这个时间戳，会跳到完全错误的位置。

而且这不是一处。构造 AI 用的时间戳文本的地方有三处
（`background.js` 的本地路径、Supadata 同步返回、异步 job 返回），
只改显示的那一处，等于让**显示的和送给模型的**对不上。

### 已修（`fcfc427`）

时间戳超过一小时时用 `H:MM:SS`。三处构造的地方用同一个函数，
显示的和送给模型的永远是同一个格式。

### 这一处比上游多做了三件事

**第一，格式化只有一个地方。** 上游改的是 `formatTimestamp` 这一个函数，
而我们这边构造时间戳的地方有**六个**：读本地字幕的、读 Supadata 同步返回的、
读 Supadata 异步 job 返回的、面板显示笔记的、面板显示章节的、
以及内容脚本在页面上画的。

如果只改显示的那一个，就会出现「用户看到 `1:30:00`，模型看到 `90:00`」，
**点一下跳到完全错误的位置，而且不会有任何报错**。所以现在：

- 格式化只有 `settings.js` 里的 `YTD_SETTINGS.formatTimestamp` 一个实现；
- 解析（把时间戳变回秒）也只有 `YTD_SETTINGS.parseTimestampToSeconds` 一个实现；
- 其余五处全部调它。**改一处就能改全部**，因为没有第二份实现。

**第二，提示词也要改。** 模型被要求照抄字幕里的标记。如果字幕写的是 `[1:30:00]`，
而提示词只教了 `[M:SS]`，模型会自己"纠正"成 `90:00`。
`prompts/analysis.md` 现在两种形状都教，并且明确写「照抄，不要转换」。

**第三，字幕长度解析器也改了。** `transcriptLengthSeconds` 原来用
`/\[\d+:\d{2}\]/` 找标记，遇到 `[1:30:00]` **一个都匹配不到**，
于是长视频的时长被当成 0，模型收到的「视频时长」是错的。
现在两种形状都认。

### 变异验收（3 个，全部被抓住）

| 变异 | 结果 |
| --- | --- |
| 格式化不输出小时部分 | 抓住 |
| 解析器只认旧的形状 | 抓住 |
| 面板显示存储的字符串而不是秒 | 抓住 |

`tests/timestamp-over-one-hour.test.js`（15 个测试）不检查源码里有没有某个字符串，
只检查**行为**：请求里真的带着 `[1:30:00]`、面板真的显示 `1:30:00`、
两条不同的字幕来源产出的标记**完全一样**。

## 三、#12：播放进度轮询太重

### 事实

播放进度每 500ms 跑一次。每一次都走 `relayToContent`，而那条路要
`chrome.tabs.query` 找 YouTube 标签页，最多三次查询。**每半秒三次查询**。

### 已修（`cd3e6aa`）

面板已经知道 YouTube 标签页的 id，直接问它。失败了才走老路（标签页可能已经关了）。

### 变异验收

测试里让「直接问」和「走中继」给出**两个不同的答案**（30 秒和 0 秒），
读错哪一条都会得到错的那个数，所以测试不可能碰巧通过。

## 四、#14：翻译批次失败后不重试

### 事实

翻译失败一次，这一段就永远停在原文。`interfaceTranslationFailures` 一进来就
永久放弃，用户看到的是一个「重试」按钮——**而用户不一定点**。

翻译是**花钱**的。网络抖一下，一段字幕就再也回不来了。

### 已修（`02a3a90`）

可恢复的错误（限流、超时、模型输出被截断）自己重试，带退避。
配置错误（Key 错了）不重试——重试也不会好，那种情况交给用户。

**自动重试用尽之后**，才进失败集合。

退避用 `setTimeout` 链，不用 `Date.now` 算等待——所以测试里的假时钟
能确定地驱动它，测试不用真的睡三秒。

### 变异验收（3 个，全部被抓住）

| 变异 | 结果 |
| --- | --- |
| 根本没有自动重试 | 抓住 |
| Key 缺失被当成可重试 | 抓住 |
| 重试用完之前就进了失败集合 | 抓住 |

## 五、#11 的 `48fe87f`：没有字幕的视频反复烧额度

### 事实

一个没有字幕的视频，**每一次**打开都要重新问一次 Supadata。
每一次都消耗一个 credit。用户反复点开同一个没字幕的视频，
额度就在流掉，而屏幕上显示的只是「这个视频没有字幕」。

### 已修（`c452b60`）

- 只缓存「这个视频的属性」类的失败（`NO_TRANSCRIPT`、`EMPTY_TRANSCRIPT`），缓存 24 小时。
- **不缓存**临时性失败（限流、Key 无效、额度用尽、超时、网络错误）——那些必须能立刻重试。
- 同一时刻的多个触发合并成一次请求。
- **本地路径不被失败缓存挡住**：本地读到了，用户照样拿到字幕。

### 三处我们没有照抄上游

**第一，命名空间是分开的。** 上游把失败写进 `digest_failed_${videoId}`
**和** `digest_${videoId}`。后者不能要：`digest_*` 是面板的缓存，
面板是它**唯一**的写者、读者和清理者（它自己按 20 条 / 30 天淘汰）。
worker 往那里写，就是多了一个写者，而且撞上淘汰逻辑。
所以失败缓存用自己的命名空间 `ytd_transcript_failed_*`，
面板的淘汰逻辑完全看不见它，它自己清理过期条目。

**第二，用户的「重试」必须真的重试。** 面板本来就有重试按钮。
如果失败缓存把重试也挡掉，那个按钮就是在**骗用户**：
点了没反应，也不花钱，看起来像「没字幕」，其实是可以重试的。
所以面板的重试按钮发 `force: true`，worker 忽略记忆、真的去查一次，
**这一次额度是用户自己的决定**。

一天之内偶然重复打开（面板开着、切标签页回来、笔记流程同时触发）
最多花一个额度；用户主动按重试，是用户的决定。
**只有这一种读法能让「最多一个额度」和「永远不会卡死」同时成立。**

上游的版本两样都不成立：它的后台缓存会把重试也一起挡掉。

**第三，成功结果不进后台缓存。** 面板自己缓存 `digest_${videoId}`，
笔记流程从那里读。后台再存一份成功结果只是多一份会过期的副本。

| 变异 | 结果 |
| --- | --- |
| 失败从来不读 | 抓住 |
| 失败从来不写 | 抓住 |
| 写进面板的 `digest_` 命名空间 | 抓住 |
| 限流也被记住 | 抓住 |
| 同一视频两个调用者付两次钱 | 抓住 |

## 六、这一轮之后又查出来的四个缺陷

门禁跑通之后，我按「还能挑出什么问题」再走了一遍产品。
下面四个，三个是从商店截图里看出来的，一个是查 API 时撞上的。
它们都不是上游带来的，是我们自己代码里的问题。

### 一、面板把后台写的英文句子直接摆给用户看（`1418fb8`）

**事实。** worker 报错时带的是一句英文句子
（"No subtitles found for this video."），面板优先显示 worker 给的 `message`，
自己的文案只是兜底。于是中文界面上的失败提示是一句英文。

**根因不是「忘了翻译」，是分层错了。** worker 是服务层，它没有语言；
面板才是有语言的那一层。worker 一旦开始写句子，它写的语言就跟着后台走，
而后台的语言不是用户的语言。

**改法。** worker 只说**代码**（`NO_TRANSCRIPT`），不说句子；
面板把代码翻成人话。代码是语言中立的，句子归面板。
服务商自己说的话仍然原样显示——那是它的原文，替它翻译就是替它说话。

### 二、AI 失败时不说缺的是哪个服务商的 Key（`582d89f`）

**事实。** `NO_AI_KEY` 只说「没有 Key」，不说哪个服务商。
三个服务商的 Key 并排存着，用户不知道该去填哪一栏。

**改法。** worker 在失败里带上服务商的**名字**。名字是数据，不是文案：
面板把它填进句子里，一句一句地说给用户。

### 三、OpenCode Go 这个服务商在产品里从来不能用（`7fc5e77`）

**事实。** 这个网关按会话 ID 路由，没有 `x-opencode-session` 头就返回
400 `MissingSessionID`。产品从来不发这个头，所以每一次请求都在到达模型之前
被挡回来，用户看到的是一句解释不了的错误。

**改法。** 发一个稳定的会话 ID：浏览器随机生成一次、存在本地、只发给那个网关。
它是随机的，不含关于用户的任何信息，别人也拿不到；
同一个 ID 一直用，网关才能复用它已经读过的提示词。
头名放在服务商登记表里，不是散在代码里的一个 if。

### 四、每个出错页面有两条「重试」路，只有一条是活的（`ad34081`）

**事实。** 错误按钮的处理器里有一条兜底的重试，而每个失败页面又装了自己的
一个动作。按钮只会走后一条，前一条是死代码。
更要紧的是，按钮上的文字是按「有没有传 action」猜的，
所以一个「打开设置」的动作有时会显示成「重试」。

**改法。** 屏幕和它的动作放在一起：出错的那个页面决定按钮做什么、按钮写什么。
默认动作是「再查一次」，因为用户没法重试的失败是死路。

**顺带查出来的一条**：盯着这条重试的变异脚本，一直盯的是那条死路，
所以它从来没红过。是这条缺陷把它暴露出来的。

## 七、这一轮的门禁状态

```
扩展测试：522 / 522 通过
发布检查：27 个允许清单文件，通过
后端测试：182 / 182 通过（真实 PostgreSQL 16）
变异验收：89 个变异，全部被抓住
  （本地字幕 23、面板 27、付费请求 14、词汇 11、失败缓存 11、时间戳 3）
```

后端测试要在**真实的 PostgreSQL** 上跑才有意义。容器里没有设置
`POSTGRES_USER`，所以角色名要用镜像名推出来（`postgres:16-alpine` → `postgres`），
连接串也必须用 `postgresql://` 开头——测试自己会检查这一条。
用 `postgres://` 连接的话，168 个测试里有 2 个被跳过，
另外 13 个真库测试根本不会跑——测试套件看起来是绿的，其实什么都没测。

连接串长这样（端口是容器映射出来的那一个）：
`postgresql://postgres:audit@127.0.0.1:55432/auditdb`

**变异脚本会过期，这是它的代价；代价必须有人付，不能假装它还在跑。**
这一轮里，`mutation-check.py` 的 M1/M4、`mutation-vocabulary.py` 的 M3/M8/M9
一开始就对不上代码了：脚本里抄的那几行旧代码已经不在了。
脚本会**大声报错**（找不到目标就退出），不会假装通过——
但一个报错的脚本等于没有门禁，所以这一轮把它们都修好了。

写完这一节之后又发现第三处：`mutation-transcript-cache.py` 的 M11 一直在盯着
一条**死路**——错误按钮的兜底重试。那条路在面板统一了失败页面的动作之后
就没人走了，所以那个变异怎么改代码都还是绿的。
「一个一直绿着的变异」和「一个报错的脚本」一样，都是没有门禁。

## 八、这一轮暴露出来的一件事

四个 PR 全部是**我们自己代码里已经存在的缺陷**，上游只是先发现了它们。

这说明一件事：**我们这一轮做的「审查」有一个盲区。**
前几轮的审查是从「产品体验」出发找问题的，所以能找出「失败看不见」「登录是别人的钥匙」
这类问题；但它不会去看「一小时以上的时间戳算错了」这种**只在特定输入下才出现的算术错误**——
因为那需要有人写一个 90 分钟的视频，或者去读别人的 issue。

**两条路都要走。** 一条是像前几轮那样从用户的眼睛往里看，另一条是去读别人的报告，
然后**在自己的代码里验证它是不是真的存在**。调研文件第四节就是这件事的清单：
八个 PR 声称修的缺陷，逐条在我们自己的代码里查证，全部为真。

**没有验证过的上游 PR 一个都不该合。** 本轮合进来的四个，每一个的「问题存在」
都是在我们自己的代码里确认过的，不是抄上游的描述。
