# ADR-003: 资料库放在本地缓存，不上服务器

## Status
Accepted（2026-10-20）

## Background

第一轮的结论：产品最大的缺口是**资料库 / 历史记录**——摘要被缓存了，但用户没有任何入口能看到过去的摘要，而缓存还会在 20 个视频 / 30 天后静默淘汰。

「让用户能看到自己的过去」有两个实现方向：

| 方案 | 做法 | 代价 |
|---|---|---|
| A. 面板内的资料库 | 读扩展本地的 `digest_*` 缓存 | 无后端改动；但受 20 视频 / 30 天限制 |
| B. 服务端的资料库 | 新增 `digests` 表 + API + 同步推送 | 需要新表、新路由、新的同步载荷；**并且要在服务器上存整份字幕和 AI 概览** |

## Decision

**先做 A（本地），把 B 留作 V2 的候选，并且把限制如实写在界面上。**

理由：

1. **B 的隐私代价是实打实的。** 存整份字幕等于在用户自己的账号下囤积一份完整的视频文字稿。`PRIVACY.md` 现在的措辞是「同步服务保存你的笔记、词汇和复习进度」——加一份字幕库就要重写这一整节，并让同步服务从一个「笔记备份」变成「内容存档」。对一个要拿给别人看的产品来说，这是个不小的定位变化。
2. **A 立刻可用，且是零新增数据面。** 缓存已经存在，`evictOldCacheEntries` 已经实现了淘汰。资料库只是把它**显性化**。
3. **A 的限制是可以诚实说明的。** 「你最近 20 个视频 · 保留 30 天」不是 bug 的话术，是一句真话。真话不伤产品，含糊才伤。

## Consequences

- 面板新增 **Library 标签**：列出本地缓存过的摘要，可搜索、可重新打开。
- 界面上必须写明保留范围和淘汰时间，不能让用户以为自己的资料被系统吞了。
- 缓存淘汰本身也要提示：现在缓存满了是静默删除最旧的，用户回头找昨天的摘要会以为产品坏了。
- **B 留作 V2 候选**：如果用户开始抱怨「我的资料库只有 20 个」，再上服务端版本。届时的迁移路径是清楚的——本地缓存里的条目在过期前可以推上去。

## Alternatives considered

- **直接做 B**：功能上限更高，但隐私定位变化大、后端工作量大，而且**在没有验证用户真的需要永久档案之前**就扩大了服务器承担的数据面。**否决**——先证明需求，再扩数据面。
- **什么都不做**：继续让缓存静默淘汰。**否决**——这是第一轮点名的最大缺口。
