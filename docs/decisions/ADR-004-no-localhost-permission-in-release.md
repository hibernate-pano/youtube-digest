# ADR-004: 发布版 manifest 不携带 localhost 主机权限

## Status
Accepted（2026-10-20）— 已执行，提交 `829025d`

## Background

`manifest.json` 的 `host_permissions` 里长期躺着 `http://localhost:8787/*`，为的是让开发者能把扩展指向本地跑的后端。

问题是这个 manifest 同时也是**发布出去的 manifest**。

## Decision

**发布版不携带 `http://localhost:8787/*`。本地开发时手动加回去，打包前拿掉。**

理由：

1. **它是一个真实的安全敞口，不只是「不必要」。** 扩展带着这个权限，意味着**用户自己机器上任何监听 8787 端口的进程**都有可能收到扩展发出的请求——包括用户的笔记和 GitHub 会话令牌。发布一个「能连到用户本机端口」的扩展，责任是产品负责人的，不是用户的。
2. **它和隐私政策是矛盾的。** `PRIVACY.md` 的权限清单从来没有提过 localhost。政策少说了自己实际要的权限——这正是商店审核会对照 schema 逐条核的东西。
3. **它对本地开发没有价值。** 开发者本来就要改 `settings.js` 里的 `SERVER_BASE_URL`，多改一行 manifest 不构成额外负担。
4. **商店审核会问。** 「一个学习类扩展为什么要访问 localhost」是那种答起来很啰嗦的问题。答不清楚的权限，最好没有。

## Consequences

- `server/SETUP.md` 现在写明本地开发时如何把这一行加回来，并明确要求**打包发布前必须去掉**。
- 发布门禁新增一条测试：任何指向 `localhost` / `127.0.0.1` / `[::1]` / `0.0.0.0` 的主机权限都会让发布失败。**没有测试，下一个加本地后端的人会把它悄悄加回来。**
- `optional_host_permissions` 仍然是「不引入」的立场（`tests/release.test.js` 已有断言）：运行期按需申请主机权限是更彻底的方案，但为了一条开发用路径引入它不值得。

## Alternatives considered

- **改成 `optional_host_permissions`，由用户点按申请**：更彻底，但为一个开发场景引入运行期权限申请的用户体验成本，明显高于收益。**否决**。
- **保留在 manifest 里，但在隐私政策里披露**：披露能解决合规，解决不了敞口本身。**否决**——能不做就不做。
