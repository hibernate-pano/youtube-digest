## 一、事实：两边现在差多远

```
fork 点            d03e1f6
上游 main 之后     3 个提交（全部已合并）
我们这边           131 个提交
代码量差异         +44,359 / -1,750，122 个文件
```

我们多出来的东西，上游**一条都没有**：

- **整个 `server/`**：Cloudflare Worker + Neon Postgres + GitHub OAuth + 网页
  Dashboard。上游的定位是「纯本地、无开发者服务器」（它自己的 README 这么写）。
- **`cloud-sync.js`**：扩展侧的同步层（每账号命名空间、冲突合并、删除墓碑）。
- **词汇本 + 间隔复习**：面板的 Words 标签、复习卡、后端的 `vocabulary` /
  `review_items` 表。
- **资料库**：30 天缓存，到期自动清。
- **面板从 3 个标签扩到 5 个**。
- **设计令牌系统**（`tokens.css` / `tokens.js`）、**可访问性**（焦点圈、弹窗圈住
  焦点、`prefers-reduced-motion`）、**失败可见**（可见提示条 + 15 个错误码的
  人话）、**运行时韧性**（请求截止时间、存储写满自愈、登录绑定发起设备）。

**上游的 `main` 上没有一样我们没有的东西。** 逐个核对：

| 上游 main 的内容 | 我们的状态 |
| --- | --- |
| transcript search（`5462cae`） | ✅ 有，`tests/transcript-search.test.js` 在 |
| 通用翻译 / interfaceBatch（`5462cae`） | ✅ 有，`interfaceBatch` 三处都在 |
| `prompts/translation.md` | ✅ 有，而且我们的更长（多了界面内容翻译和生词那两段） |
| 面板在非 YouTube 标签页自动关闭 | ✅ 有（`chrome.sidePanel.setOptions`） |
| 演示图（`bb2f7b1`） | ✅ 有，而且**更新**：我们 10-20 重新截的，是五标签页的新界面（`00ae3f4`）。上游那两张还是三标签页的旧界面，尺寸也不对（商店要 1280×800，上游是 2660×1560） |

所以「把云端拉下来」在这个层面上的实际效果是**把我们更新过的演示图换回旧的**。

## 二、真正有价值的东西在 8 个未合并 PR 里

上游从 8 月中到 9 月底一直在收 PR，`main` 停在 `bb2f7b1` 没动，但社区提了 8 个
有实质内容的 PR。我把每个 PR 的代码都读完了。

### PR #10　本地抓字幕，Supadata 降级为备选（作者 Hahn Chan，8-12）

**它做什么**：从 YouTube 页面自己的 player state 里读出字幕轨道的 `baseUrl`（这个
URL 已经是签过名的），用 `fmt=json3` 直接去 YouTube 的 timedtext 端点取字幕。
失败才回落到 Supadata。

**为什么我们要**：

1. **省钱**。Supadata 的免费额度是每月 100 条。本地抓取不消耗任何额度。
2. **产品更完整**。额度用完时，产品不是「报错让你去充值」，而是**照常用**。
3. **少一次数据外发**。字幕不出浏览器，隐私政策里「哪两类数据会离开设备」要
   少写一类。

**代价**：

- 依赖 YouTube 的页面内部结构。YouTube 改了就失效——但它有 Supadata 兜底，
  失效的后果是「退回付费路径」，不是「产品坏掉」。
- 需要 `chrome.scripting` + `world: "MAIN"` 读 `ytInitialPlayerResponse`——这个
  能力我们**已经有了**（`getPlayerVideoDetails` 就是这么做的），所以不新增权限。
- 隐私政策（中英两版）要改：Supadata 从「必须」变成「备选」。

**判断：拉。** 这是 8 个 PR 里价值最高的一个，因为它同时解决钱、完整性和隐私
三件事。

### PR #12　超过一小时的视频 + 直接问标签页要播放进度（作者 Leonardo，8-17）

**它做什么**：两件事。

1. `formatTimestamp` 在视频超过一小时时输出 `H:MM:SS` 而不是 `M:SS`。
   **这是真 bug**：一个 90 分钟的视频，90 分钟之后的时间戳全部显示成 `90:00`，
   和第 90 分钟**完全一样**。用户点时间戳会跳到完全错误的位置。
2. 播放进度轮询先直接问已知的标签页（`chrome.tabs.sendMessage(youtubeTabId, …)`），
   失败了才走 background 中继。

**第 2 点的性能账**：我们的 `relayToContent` 每次都要 `chrome.tabs.query` 找
YouTube 标签页（最多三次查询），而播放轮询**每 500ms 跑一次**。直接问已知的
标签页省掉这一整套查询。

**判断：拉。** 两个都是我们代码里能确认存在的缺陷。

### PR #14　翻译批次失败自动重试（作者 yandw，9-9）

**它做什么**：翻译批次失败时按 2s / 4s 的退避自动重试，最多 3 次。密钥错误和
鉴权错误不重试（重试也不会好）。

**为什么我们要**：翻译是**花钱**的。我们现在的逻辑是：批次失败 → 这一段进入
`interfaceTranslationFailures` → 用户看到一个「重试」按钮 → **用户不一定点**。
一个网络抖动就让一段字幕永远停在原文。PR #14 的逻辑是对的：可恢复的错误
（限流、超时、模型输出被截断）自己重试，只有配置错误才交给用户。

**判断：拉。** 但要注意我们的 `interfaceTranslationFailures` 语义是「不再自动
重试」，直接套用 PR #14 需要把两者接起来：自动重试用尽之后，才进失败集合。

### PR #11　四个提交（作者 bubb，8-13 到 9-01）

**它做什么**：

| 提交 | 内容 | 判断 |
| --- | --- | --- |
| `668ec07` | YouTube 页面上叠一层双语字幕（跟随播放滚动） | 不拉：新产品线，而且**它自己会烧 token**——每一行字幕都要翻译。 |
| `3f94b5b` | 任意网页（不限 YouTube）选词翻译 | 不拉：要给 `http://*/*` + `https://*/*` 全站内容脚本权限。这是**上架时最敏感的一条权限**，为这一个功能不值得。 |
| `48fe87f` | 缓存失败的 Supadata 查询 | **拉**：见下。 |
| `99623de` | 选词翻译防抖 + 会话内缓存 | 不拉（同上） |

**「缓存失败的查询」值得单独说**：现在一个没有字幕的视频，**每次**打开都要重新
去问 Supadata 一次——每一次都消耗一个 credit。用户反复点开一个没字幕的视频，
额度就在流掉，而屏幕上的反应是「这个视频没有字幕」。缓存这个失败结果，
用户就只会被扣一次。

**判断：只拉 `48fe87f` 那一小块。** 其余三个是产品线扩张，不是缺陷修复。

### PR #16　章节上方的「执行摘要」（作者 ddcarolyn，9-13）

**它做什么**：让 AI 多输出一段 `execSummary`（一句话主张 / 2-4 条结构 /
1-3 条可执行结论 / 带时间成本的裁决），画在章节上面。

**我们已经有 summary 了**，但形态不同：我们的 `summary` 是「2-4 句说明这个视频
在讲什么、结论是什么」；它的是结构化的四段式，还带「这个视频值不值得你看，
6 分钟看完还是跳到 12:30」。

**判断：先不拉。** 理由有三：

1. 它的 prompt 改动很大（加了几十条禁令），会挤掉我们 `analysis.md` 里现有的
   章节覆盖规则——那条规则（最后一个章节必须超过视频的 75%）是我们自己修过的
   bug（`a673386`）。
2. 它要加 `ANALYSIS_SCHEMA_VERSION = 2`，让所有旧缓存失效重算——**要花钱**。
3. 它的 UI 是一套新的卡片，和我们现有的 Summary 标签页重复。

**如果要做**，正确做法是**只取它的 prompt 里那段「结论要有时间成本和下一步动作」
的约束**，加进我们现有的 `summary` 字段，不改结构、不改缓存版本。这是我下一轮
可以单独做的一件事。

### PR #15　自定义 API 地址和模型（作者 yandw，9-9）

**它做什么**：让用户填自己的 base URL 和 model，保存时做一次连通性校验。

**为什么不拉**：

1. **和我们的定位正面冲突。** 我们是「三服务商 + 密钥隔离」：DeepSeek /
   MiniMax / OpenCode Go 各自独立，权限各自独立，请求只发给选中的那一家。
   加一个自由填的 base URL，等于允许用户把字幕发到**任何**地址——那我们的
   隐私政策（哪些数据会离开设备、发给谁）就守不住了。
2. **它自己也知道这一点**：帮助文案里写着「如果域名不是 api.deepseek.com，
   需要把它加进 manifest.json 的 `host_permissions` 并重新加载扩展」。**让用户
   改 manifest 意味着改完要重新打包**——这就不是装完即用的产品了。
3. 我们的 `options.html` 里已经有一段「本地改编」说明 + 一段给编程 Agent 的
   安全提示词，**那才是「我想用别的模型」的正路**：改自己的副本。

**判断：不拉。** 定位问题，不是实现问题。

### PR #13　多语言多 AI 的大改（作者 Beccaa2023，8-18）

19 个文件、+2396/-822。重写了 `settings.js`（+219）、`background.js`（+507）、
`sidepanel.js`（+411），README 换成了另一个项目的（还带着 GitHub 仓库链接
`Beccaa2023/YouTube-Digest-Multilingual-Language-Learning-Multi-AI`）。

**判断：不拉。** 它是**另一个产品**：多源语言、多目标语言、多个 AI 可选、放弃
单账号同步。我们的同步层、词汇本、复习、Dashboard 在它那套里全都不存在。
合并它等于**放弃我们这一轮的全部工作**去换另一个方向。

### PR #17　B 站支持（作者 Clawborn，9-28）

新增 `platforms.js` / `bilibili-content.js` / `bilibili.js`，把视频身份抽象成
`{platform, id}`，manifest 加 `https://www.bilibili.com/*`。

**判断：不拉，但值得记一笔。** 抽象本身是对的——我们现在把 YouTube 的 videoId
直接当主键，B 站支持会逼出一个平台层。但这是一个**新平台 = 新字幕源 + 新内容
脚本 + 新缓存键 + 新隐私披露**，工作量按周算，而且我们的产品名、隐私政策、
商店材料全都要重写。

**现在能做的是**：把 `platforms.js` 那个「视频身份解析」的想法记下来，等有人
真的要做第二个平台时再抽。我们**现在不要**为还没有的第二个平台付架构税。

## 三、为什么「完全基于云端最新来做」是错的方向

你提到「我们现在的更新可以完全基于云端最新的来做，这样更好，可以兼容两边的
优点」。我把这句话拆成三段来检验：

### 「以云端最新为基础」

上游 `main` 的最后一个提交是 **2026-08-27**。我们 HEAD 是 **2026-10-20**。
上游 main 上**没有任何一个提交比我们的旧**——三个提交全部是 8 月的，早就合了。

以它为基础，等于**以一个 8 月 27 日的版本为基础**，把我们 10 月做的全部工作
倒回去。不是「兼容两边的优点」，是「放弃我们这一边」。

### 「兼容两边的优点」

这正是 `6c6e08e`（10-05 那次合并）已经做过的事，而且**已经做完了**。那次
合并的手记在 `docs/UPSTREAM-MERGE-PLAN.md` 和 `ADR-001` 里：8 个冲突全部手工
解过，保留了上游的 transcript search 和通用翻译，保留了我们自己的 OAuth 同步、
三服务商、词汇复习链。测试从 82 个变成现在的 434 个。

**两边能兼容的部分，已经兼容了。** 剩下的 8 个 PR 不是「上游的更新」，是
**社区的提案**——大部分是别人想把项目带向别的方向（多语言、全站翻译、B 站、
自定义端点）。那些不是「云端最新的优点」，是「别人的主意」。

### 真正该做的

不是「拉 main」，是**从 8 个 PR 里挑出真正的缺陷修复，一个一个地、以我们
的架构方式合进来**。这 4 个值得拉：

| 顺序 | PR | 为什么这个顺序 |
| --- | --- | --- |
| 1 | **#12** | 纯 bug 修复，两处，零架构影响，30 分钟 |
| 2 | **#14** | 纯 bug 修复（网络抖动 = 丢翻译），零架构影响 |
| 3 | **#11 的 `48fe87f`** | 纯 bug 修复（没字幕的视频反复烧额度），零架构影响 |
| 4 | **#10** | 价值最高（省钱 + 完整 + 隐私），但要改隐私政策两版、且引入对 YouTube 页面内部结构的依赖 |

**这四个都已经在我们代码里验证过「问题真的存在」**（我逐条查过，见下），
所以合进来不是「引入别人的代码」，是「修我们自己发现的 bug」。

## 六、这次调研做了什么（可复核）

```bash
git fetch upstream --prune
git fetch upstream '+refs/pull/*/head:refs/remotes/upstream/pr/*'   # 8 个未合并 PR
git merge-base upstream/main HEAD                                   # = upstream/main，已全合
git merge-tree --write-tree --name-only HEAD upstream/main            # 无冲突、无新增文件
git log --oneline d03e1f6..upstream/main                             # 3 个提交，全合
git diff --stat upstream/main HEAD                                    # +44,359 / -1,750
```

八个 PR 的每一个都读了完整 diff（`git diff $(git merge-base …) upstream/pr/N`），
并逐条核对了它们声称修的缺陷在我们代码里是否真的存在。**没有合并任何东西**，
这一轮只做调研。
